## Background & Goals

现有系统以采购、收货、销售日结、成本核算和资金流水为中心，操作项和表单字段超过实际需求。用户主要通过 ChatGPT 描述收支，希望快速记账，并直观看到收入、支出。

已明确的需求：

- 整个应用使用一本账，不区分店铺；新业务表和接口不包含 `shop_id`，不增加替代性的账本选择。
- 分类只有一层，不使用父子分类。
- 一笔记录代表一笔已经发生的收入或支出，不设置待支付、待收货或结账状态。
- ChatGPT 是主要录入入口；后台用于看账、查账、改错和设置分类。
- 分类预先设置，日常记录尽量自动匹配；系统内部字段不要求用户填写。
- 彻底替换旧业务：旧业务表可以物理删除，旧模型、服务、后台页面及 MCP 工具同步清理，不长期保留两套实现。

目标是替换现有业务模型，而不仅是隐藏复杂表单。完成标准包括旧业务代码和旧业务表的实际退役，不以隐藏菜单或停用接口作为最终交付。金额统一按人民币处理；账户和账户间转账纳入本次扩展，但转账不计入收入、支出或期间结余。

## 一、目标数据结构

新增两张核心业务表。暂定名称为 `bookkeeping_categories` 和 `bookkeeping_entries`，实施前核对项目命名约定。保留现有登录、OAuth、必要授权和操作审计基础设施，不为简单记账增加新的业务层级。

### 1. 分类表 `bookkeeping_categories`

| 字段 | 设计 |
|---|---|
| `id` | 内部主键 |
| `name` | 分类名称 |
| `direction` | `income` / `expense` |
| `sort_order` | 显示顺序 |
| `is_active` | 是否可用于新记录 |
| `created_at` / `updated_at` | 自动维护 |

约束：

- 无 `shop_id`、`workspace_id`、`ledger_id`、`parent_id`。
- 同一收支方向的分类名称唯一。
- 被引用的分类不得硬删除，只能停用；停用后历史记录仍可查询。
- 记录说明修改不受原分类停用影响；新记录或改选分类必须选择启用项。
- 分类改名后，历史记录显示新名称；更名操作保留审计。
- 已有记录的分类不得变更收支方向，避免破坏历史统计。
- 初始分类以用户常用项目为准，提供少量默认项及“其他收入”“其他支出”，不自动扩张为细分类树。

### 2. 收支表 `bookkeeping_entries`

| 字段 | 设计 |
|---|---|
| `id` | 内部主键 |
| `public_id` | 提供给 MCP 等外部入口的稳定标识 |
| `direction` | `income` / `expense` |
| `amount` | 正金额，使用定点小数，精确到分，不使用浮点计算 |
| `category_id` | 单个分类外键 |
| `occurred_on` | 实际收付日期，默认应用约定时区的当天 |
| `description` | 可空的简短说明 |
| `source` | `chatgpt` / `admin` / `legacy_import`，由服务端确定 |
| `revision` | 修改版本，防止覆盖并发更新 |
| `created_by` / `updated_by` | 操作人，由服务端填写 |
| `voided_at` / `voided_by` | 撤销标记及操作人，不暴露为普通业务状态 |
| `created_at` / `updated_at` | 自动维护 |

约束与口径：

- 无店铺、项目、订单、供应商、收货、付款状态、成本版本、账户和费用归属日期字段。
- 金额必须大于零，收支方向与分类一致；修改方向时同步校验分类。
- 正常新增只需识别收支方向、金额、分类，日期默认今天，说明可空。
- 不允许把未来计划支出自动记录成实际收支；未来日期不作为普通已发生记录接受。
- 收入与支出分别求和，期间结余 = 收入 - 支出，撤销记录不参与统计。
- “期间结余”不是实际账户余额或经营利润，页面和工具反馈均不得混称。
- 为日期查询、方向和分类筛选建立必要索引，具体组合按实际查询确定。

### 3. 系统级保障

- 继续保留写入审计：记录新增、编辑、撤销的操作人、来源和必要前后值。
- 复用或简化现有幂等机制，但解除对店铺锁和 `shop_id` 的依赖。同一操作标识、相同参数重试返回原结果；相同标识、不同参数拒绝。
- 一句话多笔记录采用一次原子写入：全部成功或全部失败，不允许重试后部分重复。
- 修改、撤销按记录标识和版本执行，不凭模糊描述直接批量改账。
- 上述机制均不新增用户必填表单项。

### 4. 账户与转账扩展

新增 `bookkeeping_accounts`：名称、固定类型（`wechat`、`alipay`、`bank_card`、`cash`、`other`）、排序、启用状态、唯一默认标记及时间戳。账户类型不另建管理表。数据库以可为空的唯一标记列保证最多一个默认账户，服务在事务中锁定账户行以保证设置默认账户的并发安全；系统始终自动创建一个默认账户。

新增 `bookkeeping_transfers`：稳定标识、来源账户、目标账户、正金额、发生日期、说明、来源、创建人、更新人、撤销信息、版本和时间戳。转账仅改变账户余额口径，不生成普通收入或支出；金额必须为正、日期为今天或过去、来源与目标必须是不同的启用账户。MCP 转账写入沿用事件编号幂等和审计，修改或撤销使用版本控制。

`bookkeeping_entries` 通过增量迁移增加非空 `account_id`。迁移顺序为创建账户表和默认账户、以默认账户回填现有收支、再施加外键；不修改旧迁移。历史导入记录一律归属默认账户。默认账户不得停用或删除；被收支或转账引用的账户不得删除。账户余额由未撤销收支和未撤销转账按账户聚合计算，不改变收入、支出与期间结余的既有统计口径。

## 二、授权与单账本边界

“不区分店铺”不等于“取消权限”或“所有已登录用户自动可读写”。

- 移除本记账模块中的店铺选择、店铺成员资格检查和店铺参数。
- 保留现有身份认证、MCP OAuth 和模块级读写权限；只对明确授权使用这一本账的用户开放。
- 当前工作区、模块和店铺授权存在关联，实施第一步必须梳理依赖，给出唯一账本的授权映射，禁止把各工作区用户默认合并授权。
- 用户 ID 用于权限和审计，不用于把一本账拆成每人各自一本账。
- 不顺手删除其他模块依赖的平台表或工作区机制。若多个现有工作区的数据需合并，先列出来源和访问范围，由人工确认后再迁移。

## 三、后台功能界面

记账业务导航仅保留以下三个入口；账号及平台管理保留在独立管理区域，不混入日常记账。

### 1. 收支概览

- 默认显示本月，支持切换月份或日期范围。
- 顶部三项：收入、支出、期间结余。
- 下方显示支出分类排行（金额、占比）、收入分类汇总和最近记录。
- 点击分类跳转至带筛选条件的收支明细。
- 空数据时显示零及简洁提示，不显示利润、库存或成本待确认等卡片。

### 2. 收支明细

- 收入、支出统一列表：日期、方向、分类、带正负号的金额、说明、操作。
- 筛选：日期范围、收支方向、分类、说明关键词；提供一键清除筛选。
- 显示当前全部筛选结果的收入、支出、结余，不只合计当前分页。
- 主按钮为“记一笔”，使用轻量弹窗，不进入业务单据流程。
- 表单只有：收入/支出、金额、分类、日期、说明；日期默认今天，说明选填。
- 按方向筛选分类；记录保留后即可计入统计，无“提交入账”第二步。
- 支持编辑和撤销；撤销二次确认，内部保留审计，不物理删除历史。
- 默认不显示撤销记录，可通过辅助筛选查看，不作为日常导航入口。

### 3. 分类设置

- “支出分类”“收入分类”两个标签页，均为平铺列表。
- 支持新增、改名、排序、启停；不显示分类树。
- 不提供利润处理、成本归属、分摊和店铺选择设置。

### 4. 账户设置与转账

- 新增“账户设置”导航页，提供账户表格、轻量 CRUD、固定类型显示、当前余额、默认和启用状态。
- 收支明细展示账户、支持按账户筛选，新增和编辑表单可选活动账户，省略时自动使用默认账户。
- 收支明细提供“转账”入口；转账表单仅包含来源账户、目标账户、金额、日期和说明。

旧采购、销售日结、费用与损耗、资金流水、成本及经营项目等页面在切换后移除，并删除旧写入路径和无用实现；不能只隐藏菜单却保留可调用的旧写入口或长期维护兼容业务层。

## 四、ChatGPT / MCP 接口

重写当前 `ZhendianpuServer` 的工具集合与使用说明，不再让 ChatGPT 走“档案 → 采购 → 收货 → 付款”流程。下面为能力边界，工具名称在实现时遵循现有约定。

| 能力 | 行为 |
|---|---|
| 获取记账上下文 | 当前日期、时区、人民币口径、启用分类、当前权限和必要防重信息；不返回店铺选择 |
| 添加收支 | 一次添加一笔或多笔实际收入/支出 |
| 查询记录 | 按日期、方向、分类、关键词分页查询，返回稳定标识和版本 |
| 获取汇总 | 收入、支出、结余、分类汇总，与后台使用同一统计口径 |
| 修改记录 | 指定记录和版本修改，保留审计 |
| 撤销记录 | 指定记录和版本撤销，不物理删除 |

分类主要在后台维护，第一版不必为了覆盖所有后台功能而增加聊天工具。

交互规则：

- “今天买面粉 180，电费 260，营业收入 1200”直接生成三条记录，无采购单和付款单。
- 未说明日期默认今天，分类匹配现有分类；无合适分类可使用对应“其他”，反馈时明确实际分类。
- 金额、方向或“是否已实际收付”存在关键歧义时才追问；不要求补充商家、数量、单位、订单号、账户或收货状态。
- “准备买”“报价”“欠款未付”等不自动入账。
- 只在服务端成功后回复“已记录”；失败、权限不足、版本冲突时明确未完成。
- 同一次调用重试复用操作标识；另一次相似消费不凭日期、金额和说明相同就误判重复。
- 沿用现有 MCP 连接地址和认证的可行性在实施时核对；不得默认旧工具参数能兼容新模型。切换时更新工具清单和说明，提示客户端刷新。

## 五、旧数据与切换策略

### 原则

- 不直接修改原始建表迁移来伪装重构；新增迁移创建目标表，并使用独立的清理迁移物理删除已退役的旧业务表。
- 先形成迁移预览和分类映射，旧表只在迁移、核对和切换期间临时保留；不把永久保留旧表作为方案。
- 用户已明确要求将旧表物理删除纳入本次重构，不再将清理拆成未来独立项目。本轮只更新计划，不执行数据操作；实际执行时需明确目标环境、删除清单和数据保留策略，不将计划修订理解为立即删除现有数据或授权操作生产。
- 允许删除旧表不等于允许丢弃历史数据：默认迁移实际收付记录并备份被淘汰资料；若要放弃历史数据从空账开始，必须有明确指示，不能自行推断。

### 步骤

1. 只读盘点现有数据：来源店铺和工作区、记录数量、日期范围、有效/作废记录、收支金额、缺失分类以及旧业务关联。
2. 建立旧分类到新单层分类的人工可审阅映射；不同店铺同名分类不直接假定语义一致。
3. 优先从实际收付流水提取，按来源关联排重，不把采购、销售及其自动生成的流水各导入一次。
4. 对转账、投入/取款、退款、未付款采购、未收款销售及来源不明记录单列清单，不简单按正负金额自动合并；退款的收支归类在迁移映射中明确确认。
5. 未发生收付的单据、参考价格、成本快照不自动转成记账记录；原始表仅临时保留供核对，删除前导出归档，不再强加给新业务。
6. 导入使用稳定的来源映射或现有审计能力保存“旧表+旧记录 → 新记录”的关联，确保重复执行不重复入账，且可区分迁移记录与切换后新增记录。
7. 对已确认可迁移范围，按月、按方向核对笔数和金额；将排除项及原因列出，不要求与旧经营利润报表相等。
8. 在明确的切换点冻结旧业务写入，完成最终增量核对，启用新后台和 MCP；不做长期双写。
9. 核对通过后备份旧表结构及数据，确认备份可恢复，保存迁移映射与例外清单；不把备份长期放在应用业务表中。若切换后已有新记录，回退必须先处理新增数据，不能直接切回旧入口导致丢账。
10. 按外键依赖顺序执行独立清理迁移，物理删除已确认退役的旧业务表及相应约束，清理旧代码和无用配置。不得通过整库重建或无差别删除 `zdp_*` 的方式清理。
11. 检查最终数据库与代码：新业务只依赖新记账结构及必要平台能力，没有旧表查询、旧写入入口或悬空外键。清理迁移的回滚不能恢复已删除的数据，需使用备份和明确的恢复流程，不承诺普通迁移回滚即可恢复历史。

未确认的数据不臆造金额、日期或分类，不以零值填补未知金额。旧表物理删除属于本次重构正式范围，只有迁移核对、备份和依赖清理满足要求后才执行。

### 旧结构清理范围

- 候选删除表：旧店铺及店铺成员、经营项目、分类、商品物料、供应商、采购记录、销售记录、产品成本版本和资金流水等旧业务表。最终以实施盘点形成的逐表清单为准；共享依赖必须先解除或迁移。
- 同步删除只服务于上述结构的模型、服务、后台页面与资源、MCP 工具、校验和策略、视图、旧业务种子与工厂、失效测试及配置，更新引用方，不保留空壳兼容实现。
- 用户、登录、OAuth、模块授权和仍在使用的审计等平台表不因本次重构被无差别删除；其中对店铺的旧字段和约束按实际依赖清理，审计历史保留必要来源信息。
- 原始迁移历史不随意删除或改写；新安装应能按迁移顺序得到最终简化结构，已有数据库应能通过增量迁移达到相同结果。
